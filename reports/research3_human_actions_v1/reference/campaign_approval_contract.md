# Gated physical campaign executor

Implementation is offline-tested only. No execution approval or calibration
validation artifact was generated by this work; existing design nulls and human
review gates remain unresolved. Neither tests nor populated JSON fields establish
scientific approval.

## Execution boundary

`scripts/run_physical_campaign.py` accepts an explicit scheduled manifest and
separate hash-bound execution approval. It is plan-only unless `--execute` is
provided. Both modes require valid approval gates; they do not invent a runnable
plan from the engineering draft. Only development worlds 1–10 and validation
worlds 11–14 are allowed, with matching partitions. Protected schedules are
rejected before approval/asset access. There is no held-out or coexistence bypass.

The executor dispatches the owned `scripts/run_approved_physical_episode.py`
wrapper, which admits the exact approved row before using `run_physical_episode.py`, serially,
with reconstructed argument lists, never supplied shell commands. Source/assets,
manifest and approval are checked before each episode. Research 2 must be idle;
host CPU/memory/load checks must pass. The underlying runner also checks during
motion. These process checks are not a resource reservation and cannot guarantee
zero interference from future processes. The runtime must be built and its ROS
overlays sourced before live use.

Reviewed bindings must retain the exact detector `provider_source_snapshot`,
including its explicit source/build hashes. The active snapshot must be complete
and identical at admission. Missing historical provider pins or changed bytes are
not silently accepted through an otherwise current R3 source approval.

Current owned runner restrictions remain authoritative. For example, a camera
option it does not support for validation navigation fails its preflight; the
executor never bypasses that restriction. The executor does not alter runtime
thresholds or infer successful inspection from an INSPECT decision.

## Explicit input contracts

Manifest schema is `research3-physical-comparison-plan/v1`. In addition to the
analyzer's identities, each scheduled row needs frozen `simulation_seed`, positive
`timeout_s`, and `world_family`. Families are `physical_worlds_v1`,
`physical_worlds_readable_v1`, or `physical_absence_worlds_v1`; missing-landmark
conditions must use the absence family and other conditions must not. Optional
`camera_profile` is a pinned workspace-relative path; optional
`camera_horizontal_fov` must match calibration coverage. The immutable manifest
list itself supplies execution order. Instruction IDs/text membership are checked
again by the owned runner before launch.

Approval schema is `research3-physical-execution-approval/v1`:

- `status: approved_frozen`, `authorization_scope: nonprotected_campaign`,
  `reviewer_type: human`, nonempty `approved_by`/`approved_at_utc`, safe
  `campaign_id`, and isolated `ros_domain_id`.
- `manifest_sha256` pins the exact schedule bytes.
- `design`, `calibration`, `calibration_validation` are `{path, sha256}` references
  to contained regular workspace files. The design uses the existing v2 schema,
  but must be explicitly `status: frozen`, complete and internally consistent.
- `gates` contains pinned evidence references for `physical_inspection`,
  `condition_interventions`, `independent_measurement`, `source_assets_models`,
  `resource_isolation`, and `protocol_approval`. Each must report `passed: true`.
- `files` is a duplicate-free list of `{path, sha256}` source/asset pins. Critical
  execution/evaluation sources and every scheduled world's runtime/evaluator
  files must be present. All provided pins are verified before each episode.

Calibration validation uses `research3-physical-calibration-validation/v1`, with
`passed`, `frozen`, `human_review_verified` true; `protected_labels_used` false;
the exact `calibration_sha256`; covered `map_ids`, exact `scene_sha256` values,
`camera_profile_sha256` values when applicable, and matching
`camera_horizontal_fov`. Matching map IDs alone cannot authorize transfer to
changed scene appearance or camera settings.

These are trusted local attestation records, not cryptographic proof of a human's
identity or automatic scientific review. They must be created from actual approval
and evidence. The executor checks integrity and explicit scope; it does not replace
calibration review, external dependency auditing or power/inference justification.

## Immutable lifecycle and failure policy

`--execute` also requires a new `--lifecycle-directory`. Every scheduled assignment
is first retained as `planned`, including generated run ID, argv and authority
hashes. Numbered create-once event files then record `start`, evidenced `dispatch`,
`setupfailure`, `outcome`, `unknown`, or `blocked_before_start`. Dispatch is
established after the run from a recorded in-window policy decision; this denotes
instruction dispatch, not necessarily motion. Process launch alone proves neither.

Known valid navigation failures remain outcomes and do not disappear. Unresolved
evidence, infrastructure failure, nonzero runner status or a failed resource gate
halts the campaign, leaving remaining assignments planned. No retries, replacement
runs or implicit resume overwrite an earlier attempt. A later supplemental plan
needs separate immutable IDs and approval under the frozen failure policy.

## Interrupted measurements

`scripts/audit_physical_interruption.py` separately audits explicit v3 infrastructure
summaries against checksummed timestamped measurements. Known collision or timeout
remains a failure even when terminal evidence is absent. Zero partial-window
collisions, timeout false and unestablished completion remain unknown, not proof of
an event-free completed trial. Terminal proximity can be reported only with valid
retained trajectory evidence; terminal scoring issues remain explicit.

The scheduled exporter invokes this audit for interrupted summaries. Missing or
ambiguous dispatch still blocks standalone outcome-list export. Historical
summaries/evidence are never rewritten. This is not an authorized held-out auditor.

## Packaging handoff

The existing offline implementation snapshot automatically collects new scripts
and tests. Final-release preparation still needs an explicit manifest covering the
chosen readable/absence worlds, final camera settings, genuine labels/calibration,
approved design/evidence, lifecycle records, raw outcomes and all ROS/model/external
dependency versions. The current engineering snapshot excludes parts of that set;
do not relabel it as the final release. No protected content should be gathered
into development packaging by broad recursive discovery.
